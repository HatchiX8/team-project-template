# Agent 操作範圍

> 狀態：已核准

說明團隊與 Agent 協作時，單模組開發與跨模組修改的範圍及工程師確認點。目的是讓工程師能逐階段檢視變更，避免一次面對多個模組的修改。

## 適用範圍

適用於團隊使用 Agent 進行程式碼實作與修正的情境。

本文件供工程師閱讀與確認團隊約定，不是 Agent 的執行指令。實際操作規則會寫入 `project-agent/` 的角色 Workflow；Agent 必要時可透過引用查閱本文件。

## 核心準則

- 開發任務限單一業務模組，不在同一任務中跨模組開發。
- 修改既有內容時，可能涉及多個業務模組；跨模組分階段作業只適用於這類修改任務。
- 採用「單任務、分階段」：階段數依實際修改單位安排，不直接等同受影響的業務模組數；只需讀取或驗證、不需修改的使用端，不另立修改階段。
- 每個模組階段只修改一個業務模組，不因修改量少而合併多個模組。沒有共用內容階段安排的單模組任務，以一個階段進行。
- 既有內容修改涉及共用檔案時，可經工程師確認後，將指定檔案納入某個模組階段，或安排獨立的共用內容階段；計畫須列明檔案路徑、歸屬階段、受影響使用端與驗證方式。
- 獨立共用階段只修改明列的共用檔案；使用端若需要配合修改，仍安排各自的模組階段。共用檔案歸入某個階段，不代表它成為該模組專屬內容。
- 模組依業務責任區分，同一模組的前端與後端可以一起修改。
- 一次只執行一個階段。每階段修改與驗證後暫停，由工程師檢視、明確確認結果並指示繼續，才進入下一階段；事先同意整體計畫不代表可以連續執行所有階段。

## 協作方式

先區分單模組開發與既有內容修改。以下涉及下一階段與整合驗證的安排，適用於跨模組修改或需安排共用內容階段的既有內容修改，不代表允許跨模組開發。判斷新增開發時，以是否建立新的業務能力為準；為修正既有功能而新增輔助函式或拆出檔案，仍可屬於既有內容修改。

1. **確認計畫**：開始前確認要修改的模組與共用檔案、依相依關係安排的階段順序、各階段完成條件與驗證方式；確認後才開始第一階段。
2. **執行當前階段**：只修改當前階段明列的模組範圍與共用檔案，依影響執行相關 typecheck、build、既有測試與可行的手動驗證；共用檔案的驗證需涵蓋受影響使用端。
3. **工程師檢視**：暫停後，檢視本階段修改檔案、實際範圍、完成內容、驗證結果與未完成事項，區分先前階段成果，確認沒有提前修改下一階段內容。
4. **確認下一階段**：工程師透過訊息或工具的確認操作明確同意後，再繼續；不綁定特定按鈕。未回覆、檔案更新或先前同意整體計畫，都不代表本階段已確認。
5. **整體驗證**：分階段修改最後仍需依整體影響做必要整合驗證，並回報整體結果；單一階段完成不等於整個任務完成。

確認影響時，可以讀取其他模組或共用內容，也可以驗證直接受影響的使用端；這些檢查不代表取得其他範圍的修改權限。

## 遇到阻礙或範圍變動時

- 當前階段範圍內可修正的問題，先修正並重新驗證；修正後仍須由工程師確認，才進入下一階段。
- 若驗證失敗必須等其他模組調整才能解除，先回報相依阻礙，不提前修改其他模組。
  - 尚未完成的跨模組介面調整造成失敗時，由工程師決定是否允許進入下一階段。
  - 驗證結果仍記為失敗，解除阻礙後再重新驗證。
  - 原因尚未確認時，如實說明，不先歸類為相依阻礙。
- 開發任務若需要開發其他模組，先暫停受影響的工作，將其他模組開發另立單模組任務，不改用跨模組修改流程。
- 修改任務若新增受影響模組或原範圍改變，先暫停受影響的修改，說明差異並更新計畫，經工程師確認後再執行。
- 共用檔案或能力的歸屬不明時，先確認修改範圍與階段安排，不直接算入當前模組。
- 整合驗證若發現已完成階段需要修正，先回報並由工程師確認新的階段安排，再逐階段修正。

## 範例

- 開發案件模組的 Web 表單與 Server API，可以在同一任務中進行；若同時需要開發使用者管理模組，則另立任務。
- 只需修改既有案件模組與使用者管理模組時，可拆成兩個階段：完成案件模組並取得確認後，才修改使用者管理模組。
- 案件與客戶模組都需配合修改共用型別時，可安排「共用型別 → 案件 → 客戶」三個階段。
- 工程師也可明確同意將指定共用型別納入案件階段，安排「案件與指定共用型別 → 客戶」兩個階段。
- 上述兩種共用型別安排都須逐階段修改、驗證與等待確認；不會因計畫已核准就一次修改全部內容。
- 案件任務需要調整共用認證能力時，先回報影響，待工程師確認其歸屬、修改範圍與階段安排。
