# Agent 操作範圍

> 狀態：草稿

說明團隊與 Agent 協作時，單模組開發與跨模組修改的範圍及工程師確認點。目的是讓工程師能逐階段檢視變更，避免一次面對多個模組的修改。

## 適用範圍

適用於團隊使用 Agent 進行程式碼實作與修正的情境。

本文件供工程師閱讀與確認團隊約定，不是 Agent 的執行指令。實際操作規則會寫入 `project-agent/` 的角色 Workflow；Agent 必要時可透過引用查閱本文件。

## 核心準則

- 開發任務限單一業務模組，不在同一任務中跨模組開發。
- 修改既有內容時，可能涉及多個業務模組；跨模組分階段作業只適用於這類修改任務。
- 採用「單任務、分階段」：單模組任務為一個階段；跨模組修改涉及幾個業務模組，就拆成幾個階段。
- 每階段只修改一個業務模組，範圍限於本次需求；不提前修改其他模組，也不因修改量少而合併模組範圍。
- 模組依業務責任區分，同一模組的前端與後端可以一起修改。
- 每階段修改與驗證後暫停，由工程師檢視並明確確認，才進入下一階段。

## 協作方式

先區分單模組開發與既有內容修改。以下涉及下一階段與整合驗證的安排，適用於跨模組修改，不代表允許跨模組開發。

1. **確認計畫**：開始前確認涉及的模組、依相依關係安排的階段順序、各階段修改範圍與驗證方式。
2. **執行當前階段**：修改當前模組，依影響執行相關 typecheck、build、既有測試與可行的手動驗證。
3. **工程師檢視**：暫停後，檢視修改檔案、實際範圍、完成內容、驗證結果與未完成事項，確認變更仍在當前模組內。
4. **確認下一階段**：工程師透過訊息或工具的確認操作明確同意後，再繼續；不綁定特定按鈕。未回覆、檔案更新或先前同意整體計畫，都不代表本階段已確認。
5. **整體驗證**：跨模組修改最後仍需整合驗證，並回報整體結果；單一階段完成不等於整個任務完成。

確認影響時，可以讀取其他模組或共用內容，也可以驗證直接受影響的使用端；這些檢查不代表取得其他範圍的修改權限。

## 遇到阻礙或範圍變動時

- 當前模組內可修正的本階段問題，先修正並重新驗證。
- 若驗證失敗必須等其他模組調整才能解除，先回報相依阻礙，不提前修改其他模組。
  - 尚未完成的跨模組介面調整造成失敗時，由工程師決定是否允許進入下一階段。
  - 驗證結果仍記為失敗，解除阻礙後再重新驗證。
  - 原因尚未確認時，如實說明，不先歸類為相依阻礙。
- 開發任務若需要開發其他模組，先暫停受影響的工作，將其他模組開發另立單模組任務，不改用跨模組修改流程。
- 修改任務若新增受影響模組或原範圍改變，先暫停受影響的修改，說明差異並更新計畫，經工程師確認後再執行。
- 共用檔案或能力的歸屬不明時，先確認修改範圍與階段安排，不直接算入當前模組。

## 範例

- 開發案件模組的 Web 表單與 Server API，可以在同一任務中進行；若同時需要開發使用者管理模組，則另立任務。
- 修改既有案件模組與使用者管理模組的程式碼，可以在同一任務中拆成兩個階段。
- 修改任務涉及三個業務模組時，拆成三個階段；每階段修改與驗證後停止，工程師確認後才進入下一階段。
- 案件任務需要調整共用認證能力時，先回報影響，待工程師確認其歸屬、修改範圍與階段安排。
