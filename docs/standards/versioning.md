# 版本與發布規範

**文件狀態：草稿。**

用於對齊團隊的版本標示與發布方式，讓成員能辨識版本及其對應變更。

## 適用範圍

團隊各專案的版本號、升版、Git tag 與發布資訊。

## 版本單位

- 團隊預設以專案為單位，使用同一個正式發布版本。
- Web 與 Server 一起發布時，共用同一個版本號。
- App 或套件確實需要獨立發布時，由該專案明確記錄例外、適用範圍與版本安排。
- 本節定義正式發布版本；版本號的維護方式見下方「版本號維護位置」。

## 版本規則草案

以下內容移植自 LINE 售服系統部署文件，作為團隊跨專案規範的討論起點，尚未經團隊核准。

### 版本格式

- 版本使用日期格式 `vYYYY.MM.DD`，例如 `v2026.10.06`。
- 同一天第二次發布起加上序號，例如 `v2026.10.06.2`。

### Git Tag

- 版本 tag 只能建立在 `main`。

在 `main` 建立版本 tag 並推送，以下指令以 `v2026.10.06` 示範：

```powershell
git tag v2026.10.06
git push origin v2026.10.06
```

範例中的版本號須替換為本次要發布的版本；本文件不取代各專案的部署流程。

## 發布與 Tag 建立時機

- 日常 Commit、建立 Pull Request 或功能分支合併至 `dev`，不因此建立正式發布版本。
- 要發布的變更須已透過 Pull Request 合併至 `main`，並符合所屬專案的測試通過條件。
- 確定要正式上線時，才在 `main` 上為本次要部署的程式碼建立並推送版本 tag。
- 正式環境部署該 tag 對應的程式碼；PR 合併不等於已完成部署。
- 同一天再次正式發布時，依版本格式使用下一個序號。

## 版本號維護位置

- 正式發布版本以 Git tag 為唯一依據，不另外手動維護另一份發布版本號。
- Web 與 Server 的 `package.json` 不要求手動同步正式發布版本。
- 畫面或 API 需要顯示版本時，由部署流程傳入本次部署的 tag 名稱。
- 獨立發布的套件需要自己的版本時，依該專案明確記錄的例外安排處理。

## 發布說明

- 每次正式發布在 GitHub Release 保留一份與版本 tag 對應的發布說明。
- 發布說明包含本次新增、修正與重要變更，以及對應的 Pull Request。
- 有部署注意事項時，記錄環境變數、Migration 或相容性影響等資訊；沒有時省略。
- 發布說明以 GitHub Release 為主要維護位置，不另外手動維護重複的 CHANGELOG。
