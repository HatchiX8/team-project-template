# 需求分析與開發評估

Encoding: UTF-8

## 適用範圍與權限

- 適用於完整建立新模組前的評估；不自動套用於局部修正、除錯或重構。
- 允許無角色使用：是，限讀取相關文件與程式碼、需求討論、逐題決策及對話工作包。
- 可組合角色：developer，僅補充其修改前分析；本 Skill 執行期間仍維持唯讀，完成後停止，等待使用者另行指定正式開發任務。
- 不建立工作包 Markdown，不修改文件、程式碼、依賴或執行環境，不執行正式測試、正式 Review 或啟動子 Agent。
- 正式寫入依後續任務分流：實作須由使用者指定 Developer；必要規格與核准狀態須由 Documenter 或工程師先處理。本 Skill 不授予寫入或核准權限。
- 回答決策、完成工作包或建議可分工，都不代表已授權實作或指派子 Agent。每則訊息仍依根目錄 `AGENTS.md` 分流。

## 一、讀取依據與理解需求

- 從本次模組與需求定位必要的 `docs/project/`、`docs/modules/`、`docs/api-contracts/` 及受影響 App 的文件，讀取相關章節、文件狀態與最小直接關聯來源。不預設新對話已有其他聊天室的分析結果。
- 讀取現有實作、引用端與共用能力以確認實際影響、可沿用部分及缺口；程式碼只代表現況，不取代正式需求，也不以舊實作推定新規格。
- 區分已核准依據、草稿、使用者本次要求、已確認決策及分析推論。必要文件缺失或未核准時可繼續評估，但列為實作阻礙，不宣稱已可開發。
- 整理目標、使用者與主要情境、範圍及排除事項；資訊已明確時不重問，不把「完整模組」解讀為加入文件未要求的功能。

## 二、評估與建立決策清單

先完成指定範圍的整體分析，再呈現問題清單並進入問答，不只分析眼前的一題。

- 依需求檢查主要及異常流程、角色權限、資料與狀態、API 契約、外部依賴及既有模組的銜接；僅納入有依據且影響本次工作的項目。
- 交叉核對規則、例外、範例與適用環境，指出需求與正式依據之間的衝突、缺漏或無法執行的步驟。
- 評估受影響的 App、模組、共用能力與設定，以及各實作單元的前置條件、介面依賴和整合風險。不將未驗證的預估寫成確定事實。
- Agent 可唯讀查證的技術問題先查證；不影響需求、對外行為、資料、權限或架構邊界的內部實作細節留給 Developer，不要求工程師逐項決定。
- 每個必要決策附文件位置或直接依據、具體情境、影響及可行方向；依阻塞程度排序，標示必須於實作前解決的事項。偏好或可選改善另列，不強制加入決策。
- 沒有必要決策時直接產出工作包，不湊題數。來源不足時明示未確認範圍，不以猜測補齊需求。

## 三、逐題確認並核對整體

- 一次只問一個可獨立決策的問題，通常提供二至三個有實質差異的方案；有推薦時說明取捨，允許自訂、保留現況或暫緩。
- 收到回答後簡短記錄選擇及必要理由，核對對其他條文與已完成決策的影響；需要追加問題時說明依據，不重問仍有效的答案。
- 決策不能由沉默或預選方案推定。暫緩事項保留在工作包；會阻塞實作時，不因題目已討論過就視為解除。
- 全部必要決策有處置後，將結果放回整體流程、API 與跨模組依賴核對。需要更新正式文件或核准時列出目標與原因，不自行修改或將對話決策當成已核准規格。

## 四、在聊天室交付工作包

只在對話中輸出一份可獨立理解的最新工作包；沿用既有文件作為詳細規格，不複製整份文件，也不另建報告。固定依下列順序輸出十個標題，作為後續開發的通用交接格式；無適用內容填「不適用」，沒有未決事項時 `Open Questions` 填 `None`。只保留最新有效決策，不記錄討論演進。

| 欄位 | 內容 |
| --- | --- |
| Objective | 模組目標與預期結果 |
| Confirmed Decisions | 選擇、必要理由、對應需求，以及是否已同步正式文件 |
| Scope | 受影響模組、App、共用能力與本次範圍 |
| Out of Scope | 明確排除的工作 |
| Current Evidence | 實際讀取的文件路徑、章節、核准狀態、必要程式位置及工作區既有變更；區分規格與現況 |
| Required Changes | 以 W1、W2 等穩定編號列出實作單元、產出、可修改範圍、前置條件、共用介面與先後依賴；標示可能修改相同檔案的部分及整合工作 |
| Constraints | 已知規則與入口路徑、任務限制及授權邊界；未指定開發角色時明示尚未取得實作授權 |
| Validation | 預計採用的驗證方式、已知命令與環境前提；未知時明示待接手確認，不猜測命令，不將預計驗證寫成已通過 |
| Acceptance Criteria | 各實作單元與整體模組可觀察的完成條件及文件依據；區分實作、驗證與正式測試 |
| Open Questions | 未決事項、缺失或未核准依據、待同步文件及未查證範圍；區分阻塞與非阻塞，說明是否具備進入實作的條件 |

以最低充分資訊為準，一般工作包約 800–1,500 tokens 為軟上限；必要契約或跨模組邊界可超過，不以縮短內容犧牲可獨立理解性。

### 後續接手

- Developer 沿用有效的需求分析與決策，仍須讀取必要正式依據與現有實作，確認文件核准、來源變動、規則衝突及授權範圍；只有具體差異才補充分析受影響部分，不重跑完整問答。
- 接手者沿用這份工作包，只補足角色前置檢查、必要規則與驗證資訊；細部程式追查與實作設計在正式開發時完成，不要求分析階段預先完成。
- 工作包可直接供 Developer 使用，不要求額外 Skill。使用者也可自行搭配其他工具或 Skill；它們可引用相同工作單元、依賴、範圍與驗收條件，但不得擴大原授權。本 Skill 不規定模型選擇或派工流程。
- 工作包不取代正式文件、核准或任務授權。交付後停止，等待使用者另行指定 Developer 開發任務；不自動進入實作。
- 同一對話可引用上述工作包；若換到另一對話，由使用者提供工作包內容，不能假定可取得原對話。

## 呼叫範例

```text
團隊 Skills：requirement-analysis
任務：評估完整建立指定模組，完成必要決策後在聊天室整理工作包。
模組文件：docs/modules/<module>/
API 文件：docs/api-contracts/<module>/
```

交付後，可在同一對話直接使用：

```text
角色：developer
任務：依上述工作包完成實作。
```

若使用者另有需要，可在正式開發指令中明確指定額外 Skill；不影響上述直接接手方式。
