# 專案環境盤點與逐步整備

Encoding: UTF-8

## 目的與角色邊界

讓工程師看清專案目前能做什麼、距離目標階段還缺什麼，依依賴順序一次處理一個可檢視的項目。

- 允許無角色使用：是，限唯讀盤點、討論、對話中的決策與步驟安排；不授予寫入權限。
- 可組合角色：`developer`、`documenter`。同一時間只有一個作用中角色，不自動切換、啟動子 Agent 或建立其他聊天。
- 程式碼、依賴、工具設定、環境範例與建置設定的修改交給 `developer`；說明、規範、接線文件、文件搬移與連結整理交給 `documenter`。依檔案用途判斷，不把機器讀取的設定當成一般文件。
- 角色入口、必要來源、核准條件與驗證要求以目標專案的 `AGENTS.md` 及角色 Workflow 為準。本 Skill 不修改入口、不創造角色延續例外，也不自行核准文件。
- 「呼叫角色」在本 Skill 中指：提供具體角色與範圍指令，由工程師在下一則訊息送出。已有適用的明確角色與授權時，直接沿用該角色流程，不要求重複指定；每則訊息仍依專案入口重新判斷。
- 一個項目同時需要程式與文件時，拆成互相關聯的 Developer／Documenter 步驟。兩者各自有完成條件，不在單一角色工作中偷渡另一角色的修改。

## 來源與產出

先讀專案入口與使用者指定範圍，再讀完成判斷所需的最小直接關聯來源：

- 專案目標、目前階段、架構、開發、環境、測試及部署文件；實際位置以專案導覽為準，不要求固定目錄結構。
- 受影響 App 的規範、README、manifest、lockfile、版本宣告、環境範例、建置與品質設定，以及已存在的接線程式。
- 涉及串接時才讀取對應 API Contract 與模組流程，不為補齊清單掃讀所有業務文件。

區分已核准規範、草稿、程式實況、歷史驗證紀錄與自己的推論。文件記載「已完成」不代表本機已設定；套件列在 manifest 不代表已安裝、已接線或已驗證。不要輸出實際環境檔中的憑證或機密值。

盤點、步驟表、交接摘要預設留在對話，不自動建立報告、追蹤檔或待辦文件。只有工程師授權的正式文件工作才寫入對應位置。

## 一、判斷目前階段與本輪目標

1. 確認範圍，例如單一 Web、Server 或整體專案，以及本輪希望具備的能力。已能從指令與對話確認時不重問。
2. 根據文件與實際產物判斷目前停在需求／契約、環境準備、共用基礎、功能開發、整合驗證或交付中的哪一階段；允許不同模組處於不同階段。
3. 簡要列出判斷證據與尚未確認的部分，不只依套件安裝數量或文件是否寫完判定可開發。
4. 有同一範圍的前次盤點時，核對變動並接續，不重做已完成且未受影響的工作。

例如目標是「讓隊友完成契約後能開始功能開發」，就先完成必要執行環境與共用接線；登入流程、權限與業務 schema 等仍待契約的部分另列，不藉環境整備提前實作。

## 二、比對文件、套件與實際配置

依專案選型檢查有關項目，不把以下例子當作每個專案都必須採用的技術清單：

| 面向 | 核對重點 |
| --- | --- |
| 執行與安裝 | runtime／package manager 版本、workspace、manifest／lockfile、安裝與重建指令 |
| 環境與串接 | 環境範例、變數用途與載入方式、公開值與機密界線、代理與正式請求路徑 |
| 建置與品質 | 框架設定、型別與別名、樣式處理、lint／格式化、啟動與建置指令 |
| 共用基礎 | 僅核對已選用且此階段需要的 HTTP、狀態、語系、日期、驗證及路由備援等接線 |
| 驗證與交接 | 測試工具與指令、替身與外部依賴、文件使用方式、已知限制與核准狀態 |

對每項區分：可用、已接線但未驗證、缺設定、文件與實作不符、待工程師決策、待外部契約、此階段不需要。至少指出來源位置、實際差異與對本輪目標的影響；尚未執行的啟動或建置不能寫成通過。

唯讀盤點不安裝套件、不啟動會寫入產物的建置、不改環境檔；需要這些操作時列入後續授權步驟。

## 三、列出整備步驟並先停下

在首次修改前，交付階段結論、已具備能力與排序後的步驟表：

| 編號 | 項目與必要性 | 前置依賴／決策 | 角色 | 修改範圍 | 完成與驗證條件 | 狀態 |
| --- | --- | --- | --- | --- | --- | --- |

依阻擋程度與依賴排序，不固定項目數。每步以一個可獨立檢視的結果為單位；例如「HTTP 基礎」與「登入換票」分開，工具接線與業務功能分開。

預先列明根目錄 lockfile、共用設定或跨 App 的必要影響，不到安裝或修改時才隱含擴大範圍。非必要共用元件、額外套件與個人偏好列為可延後，不為追求完整而納入。

指出下一個最小項目與具體範圍，停下供工程師檢視清單。可略過、重排或縮小項目；不要在列完清單後同一輪把所有設定改完。

## 四、依角色完成一個步驟

工程師確認要處理的項目後：

1. 核對本則訊息的角色權限與該步驟的實際修改範圍。需要新角色或範圍授權時，提供可直接送出的指令並停下，不自行讀入另一角色後宣稱已取得權限。
2. 適用角色與範圍已成立時，依專案入口載入該角色及必要 Skill，輸出角色要求的提示，直接完成該單一步驟。
3. 缺少會影響行為、資料、權限或架構的決策時，說明具體來源、候選方案與建議，等待工程師決策。選擇方案不等同文件整份核准，也不取代目標專案要求的來源更新。
4. 文件需要先補規格時，安排 Documenter 步驟；程式完成後需要同步使用文件時，保留下一個 Documenter 步驟，不宣稱交接已全部完成。
5. 完成該角色允許的必要驗證，修正本步驟造成的問題。不自動進入正式 Review、建立測試案例或啟動 Tester；這些依專案入口另行授權。

角色指令應包含 `角色：developer` 或 `角色：documenter`、`團隊 Skills：environment-readiness`、本步驟編號、目的、允許修改的具體範圍、排除事項與完成後停下的要求。不得讓工程師重新描述已確認的完整背景。

## 五、完成後停下，接續時只推進下一步

每步結束回報：

- 本步驟完成內容、主要檔案與可觀察的結果。
- 實際驗證結果；區分通過、失敗、未執行與依修改性質免執行。
- 剩餘限制、待契約或待決策，以及尚需同步的文件。
- 更新後的精簡步驟狀態與下一個最小項目。

最後停下，讓工程師檢視本步修改範圍與內容；不把沉默或經過時間視為同意，也不在驗證完成後自動執行下一項。

收到「下一步」時，先確認上一個檢視點與下一步是否明確；可依語境視為繼續規劃或執行的意圖，但不能取代專案要求的角色與範圍。需要切換角色或新增範圍時只補交接指令；已有適用授權時直接執行，不重問已確認的選項。

新對話需工程師提供前次摘要或已有紀錄，核對目前檔案後才接續；不假定另一對話已完成驗證。全部必要項目完成時，說明已達成的階段、尚待外部條件及可延後項目，不持續新增環境準備工作。

## 呼叫範例

先盤點，不修改：

```text
團隊 Skills：environment-readiness
盤點 Web 目前階段，目標是隊友交付契約後可直接進入功能開發。
先列出必要配置、落差與逐步安排，不修改檔案。
```

工程師確認清單後，以對應角色與具體範圍接續，例如：

```text
角色：developer
團隊 Skills：environment-readiness
執行已確認清單中下一個環境接線項目，修改範圍以該項已確認檔案為限。
若實際需要擴大範圍先指出；完成必要驗證後停下，不處理其他項目。
```

文件步驟改用 `角色：documenter` 並明確列出文件對象；沒有前次已確認清單時，不使用上述接續範例推測修改範圍。
