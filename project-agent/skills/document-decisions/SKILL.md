# 文件分析與逐題決策

Encoding: UTF-8

## 目的與權限

將「分析 → 逐題決策 → 統一修改」整合為一個文件工作流程。重點是規則能否被一致理解與實際執行；命名偏好、團隊選型與格式只做簡要檢視，除非它們造成具體衝突或使用障礙。

- 預設主要讀者為工程師，命名與格式簡要檢視；使用者另有指定時依其要求調整。必要的格式、連結與內容核對仍依角色規則完成。
- 明確指定 `角色：documenter`、`團隊 Skills：document-decisions` 與文件範圍時，預設要求分析、逐題決策，並在本次納入的決策完成後統一修改這些文件；不必另寫「決策完成後修改」。
- 使用者明確要求只分析、只討論或不修改時，該限制優先於上述預設；無角色使用仍維持唯讀。
- 允許無角色使用：是，限唯讀了解、討論、逐題決策與對話草案；本 Skill 不授予無角色寫入權限。
- 正式寫入角色：`documenter`，且須明確指定文件範圍；修改要求可由上述明確呼叫的預設流程取得。
- 可組合角色：`documenter`。其他角色不在本 Skill 的組合範圍內，不自動切換角色。
- 明確限定唯讀時，選擇方案不會解除該限制。
- 依預設或明確要求執行決策後修改時，將本流程納入角色的修改前釐清；本次納入的決策完成後，在適用權限與授權範圍內統一修改。
- 角色負責入口、權限、來源判定、文件狀態、格式、驗證及回報；本 Skill 只補充分析重點與決策節奏，不重複啟動第二套分析或修改流程。
- 每則訊息依根目錄 `AGENTS.md` 重新分流。本 Skill 不建立 Documenter 的角色延續例外；只有 A／B 等回答可記入原決策脈絡，不因此取得本則訊息的角色寫入權限。

## 來源與產出

- 讀取使用者指定的文件，以及能確認其規則、例外或流程銜接的最小直接關聯來源；不擴大成全專案審查。
- 與 Documenter 組合時，由專案入口載入角色規則，沿用角色要求的 `docs/templates/documentation-standard.md`（若存在），不複製角色規則到本 Skill。
- 區分文件原文、已核准約束、工程師新決策與自己的推論。關聯文件已承擔的細節，不重複列為缺漏。
- 分析、候選方案與決策紀錄留在對話，不額外建立報告或決策檔；修改只落在使用者授權的目標文件。

## 一、分析並建立問題清單

確認文件對象、用途及本次範圍；資訊可由指令和文件判定時不重複詢問。若已有同一範圍的分析成果，核對其是否仍適用後沿用。

### 提問前完成範圍內掃描

- 列出本次目標文件，完整讀取其內容；指定資料夾時先確認其中的文件清單，不只搜尋關鍵字或讀取摘要。直接關聯來源依「來源與產出」讀取，不擴大修改範圍。
- 在對話中保留簡要覆蓋紀錄：已讀文件、主要流程與適用邊界、已核對的直接關聯來源，以及未能確認的範圍。內容太長時分批讀取並接續紀錄，不把尚未讀完的範圍宣稱為已分析。
- 先完成整個指定範圍的下列檢視，再以實際情境串接流程並交叉核對條文、例外、範例及引用來源，建立問題清單後才逐題確認；不能找到幾題就停止，也不能因逐題提問而只分析下一題。

檢視項目：

- 同份或直接關聯文件是否對相同情境給出不同要求，或與直接相關的已核准約束不一致。
- 名詞、適用對象、角色責任、前提與例外是否會導致不同解讀。
- 各流程的開始、完成、驗證、確認與交接條件能否銜接。
- 失敗、重試、回復、部分完成或範圍變動時，是否存在實際無法依規則繼續的情境。
- 是否存在多份維護來源、狀態或核准資訊，可能使讀者誤認適用依據。
- 使用者本次明確要求是否遺漏；包含 API 等對外介面描述時，是否與引用契約或約束一致。
- 範例、指令、檢查清單與預期結果是否符合正文要求；例如統一 API 回應規則是否涵蓋健康檢查範例，不能自行假定範例是例外。
- 通用步驟是否正確承接已定義或引用的例外流程；例如一般合併流程與緊急修補流程，不能只更新例外章節而漏掉操作步驟。
- 不同環境、角色與階段的適用範圍是否清楚；例如上線前驗收與部署後驗證不能僅因都是手動操作就視為同一要求，也不能未讀邊界就判定互相衝突。
- 依文件描述逐步走完主要流程，確認前一步的限制不會阻止後一步的必要操作；涉及停止寫入、維護、權限或核准限制時，核對驗證、回復與恢復服務是否有足夠的執行條件。只檢查有文件依據的情境，不為假想情境新增政策。

每個問題附文件位置、原描述、直接依據、具體情境、影響與可行調整方向。區分「已確認問題」與「補充建議／待確認」；沒有依據的完整性期待或不同但合理的設計，不當成缺失。

依影響與流程阻塞程度排序，對本次修改前需要先決策的項目明確標示 **優先處理** 並說明理由；不固定問題數或優先項目數。補充建議只有在使用者選擇納入時才加入決策安排；範圍外問題只說明影響，不自動納入修改。

先呈現目前已確認的完整問題清單、排序及簡要覆蓋範圍，不在此時修改文件。未讀來源或缺少依據時明示限制。預設接著逐題確認；使用者明確限定只做分析或檢查時，交付問題清單即可，不進入決策或修改。

## 二、一次確認一題

- 每次只提出一個可獨立決策的問題，包含題號、主題、優先標示（若適用）、簡短背景，以及通常二至三個真正不同的方案。
- 有合理推薦時標示「建議」並說明主要取捨；允許使用者自訂方案、保留現況或暫緩，不把推薦選項當成已同意。
- 一題若含有需要分別確認的政策，拆題；使用者的回答揭露必要歧義時，先問相關釐清題再往下，不自行補上政策。
- 收到答案後，用一句話記錄實際決策，再提出下一題。維持題號與決策對應；新增題目時更新剩餘安排，不因題數增加重問已完成事項。
- 核對每個答案對其他條文、例外、範例及已完成決策的影響；需要追加題目時說明具體依據與影響。沒有新依據時，不把同一問題換句話重問，也不為了補足題數新增問題。
- 工程師可修正先前決策；保留最新有效選擇，檢查是否影響其他答案，需要時只重開受影響問題。
- 等待回答期間不修改文件；不把沉默、經過時間或建議選項視為同意。
- 「保留現況」與「暫緩」都是已處理的決策。前者不改原條文；後者只在使用者同意記錄待確認事項時寫入，不以猜測方案取代。

## 三、決策完成後統一修改

本次納入的決策問題均有明確處置後，依決策表核對預計影響的文件。依預設或明確要求進行決策後修改，且本則訊息具備適用的 Documenter 權限與文件範圍時，直接執行，不再要求重複指定修改要求或核准全部答案。

- 若本次明確限定唯讀、未取得 Documenter 權限，或缺少文件範圍，保留全部決策。需要寫入時指出具體邊界，提供帶有角色、Skill 及文件範圍的指令；收到後沿用決策，不重跑問答。原有唯讀限制須由使用者明確解除。
- 多輪決策若預期使用者只回選項，最遲在最後一題說明：完成後寫入仍須依根目錄入口取得本則訊息的 Documenter 權限。可將最後答案、角色、Skill 與文件範圍放在同一則訊息，沿用本 Skill 的預設修改流程，不必重複指定讀者、檢查重點或修改要求；角色延續依根目錄規則判斷。
- 修改前重新讀取目標與工作區差異。若文件在問答期間變動，保留既有工作，只對使決策失效的差異重新詢問。
- 寫入前依本次覆蓋紀錄，將全部最新決策放回主要流程及關聯條文一起核對。各題都有答案不代表答案彼此相容；仍有需選擇的新政策或矛盾時，追加題目，完成受影響的決策後才寫入。
- 僅落實已選方案；同步處理授權範圍內必要的定義、例外、交叉引用及前後矛盾。不趁機新增未決定的政策或改名。
- 必要的新政策會影響既有決策時，先提出追加問題，不以「銜接修正」自行裁定。需要範圍外修改時，回報檔案與原因，取得對應授權後才執行。
- 決策完成不等於整份文件已核准；文件狀態依 Documenter 規則處理。若只更新說明文件而未同步 Workflow 或實作，如實標示尚未同步，不宣稱行為已改變。

## 四、核對與交付

- 逐項對照最新決策與實際修改，確認沒有漏做、反向套用或擅自採用建議。
- 重新讀取修改後的目標文件，依本次覆蓋紀錄核對流程、例外、範例及跨文件引用，確認決策已完整落實。需要新決策時回到逐題確認；單純漏套已選方案則直接補正。唯讀任務以分析及決策內容完成同樣核對。
- 檢查修改後的定義、前提、例外與關聯條文是否一致，並執行適用的 UTF-8、Markdown、相對連結與差異空白檢查；依角色規則核對章節及參照式連結。
- 只改文件時不啟動正式測試或程式碼 Review，也不宣稱程式行為已驗證。
- 與 Documenter 組合時使用角色的輸出規則，統一回報一次。中間的單題決策訊息保持簡短；交付或停止時回報完成範圍、實際檢查、限制及未解事項。
- 指定範圍已完成上述核對、已確認問題均有處置，且限制與暫緩事項已說明後即可交付；沒有新依據時不無限重掃。

## 呼叫範例

```text
角色：documenter
團隊 Skills：document-decisions
文件：docs/standards
```

若只需唯讀分析與決策，明確寫「先分析與逐題討論，不修改文件」。無角色指定 `團隊 Skills：document-decisions` 時，只進行討論及對話草案；後續需修改時再指定 Documenter、文件範圍與修改要求。
