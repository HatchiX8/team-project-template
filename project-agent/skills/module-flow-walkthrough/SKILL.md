# 模組流程逐條核對

## 邊界

- 唯讀解說使用者指定的模組文件，不自行修改文件、產生 API 文件、檢查實作或執行測試。不藉本 Skill 取得專案角色權限；遵守作用中專案入口。
- 以文件為證據，不自行補足規則、不將一般慣例當作本專案規範。使用者在討論中確認的新決定須標為「使用者補充，尚未寫入文件」，不得冒充原文。
- 先讀完指定目錄所有文件。遵守使用者限制的來源範圍；有必要引用外部 schema、ADR 或其他模組時，若來源限制不允許，僅標示依賴，勿據此斷言文件缺漏。允許擴讀時只讀必要來源並明列來源。

## 本次文件範圍

本階段維持四份模組文件，不要求新增其他文件或擴大規格。檢查職責如下：

| 文件 | 職責 |
| --- | --- |
| overview.md | 模組目的、責任、邊界、主要角色、上下游模組與不負責事項 |
| flows.md | 主要使用情境、正常流程、例外流程、狀態變化及跨模組互動 |
| data-rules.md | 資料欄位意義、驗證、唯一性、生命週期、一致性與商業規則 |
| permissions.md | 角色權限、資料可見範圍、操作限制及拒絕情境 |

先判斷問題是否屬上述職責，再套用缺失篩選。影響 API 是篩選條件，不是擴大文件範圍的理由。不將未獨立成檔視為缺失，也不要求為完整性補上本階段未承諾的功能。唯一性、資料可見範圍、模組責任等非順序步驟，仍須檢查；能歸入流程者在該條說明，無法歸入者於整體檢查列出，不硬湊成流程。

## 前置：整體商業流程檢查

讀完文件、盤點流程後，先檢查整體，再進入逐條說明：

- 依既有文件串起觸發者、必要前提、主要分支、結果與跨模組交接；核對流程能否達到 overview 的目的、責任是否有矛盾或無人承接、生命週期能否銜接，以及權限／資料規則是否使主要路徑無法成立。
- 只報告會影響整體商業流程成立的問題與職責內的非流程規則問題，附原文位置與影響；資料來源受限時明列無法判定，不把來源外事項當作缺漏。不得臆造新情境或要求完整產品設計。
- 欄位、單一驗證條件與個別例外等細項，留到對應流程逐條解說，不在前置階段展開全部問題。整體問題在後續只補充該條相關細節，避免重複報告。
- 首次輸出標示「此次共 N 條流程，目前為整體商業流程檢查（尚未開始第 1 條）」；列精簡流程清單、整體流程摘要與整體問題。若未發現，說明僅就已讀範圍未發現阻礙，不保證完整無誤。
- 前置檢查說完等待使用者核對；使用者要求繼續後才開始第 1／N 條。前置檢查不計入 N。使用者只是核對完成但未要求繼續時，維持進度。
- 中途更新 Skill 不代表自動重啟或恢復已暫停的分析。使用者要求套用新流程時，保留已核對進度，先補整體檢查再依指示續行。

## 流程盤點與進度

- 在開始逐條解說前，先依觸發條件、分支及結果建立流程清單並計數。正常流程與例外流程都計入；相同情境出現在不同文件不可重複計數。
- 共用驗證步驟不各自算一條正常流程；明列的失敗情境可獨立成例外流程。跨模組觸發與一般重新操作若分列，說明拆分理由，避免虛增數量。
- 首次回覆依前置整體檢查格式輸出；開始逐條說明時從第 1／N 條開始。數量屬本次解說拆分，不宣稱是原文既有編號。
- 每次逐條回覆第一行標示「此次共 N 條流程，目前第 i／N 條：流程名稱」。追問同一條時保持進度。
- 每次只說明一條，說完等待核對。使用者明確要求下一條或繼續才前進；暫停、討論邊界或詢問總數不得推進。
- 若文件或範圍變更導致重盤點，解釋總數與編號變動，保留已核對情境，不默默重新編號。

## 可點選的互動選項

- 需要使用者選擇處理方案、核對後是否繼續或暫停時，優先使用目前環境提供的原生互動提問工具，讓使用者可用滑鼠直接點選；不要只在正文列出 A／B／C 後要求輸入代號。
- 可使用 `request_user_input_async`；只有在目前模式允許時才使用 `request_user_input`。依實際工具能力選擇，不為取得選項介面而擅自切換模式。
- 一次聚焦一個問題，通常提供二至三個互斥且意思明確的選項；題目包含目前流程編號、必要背景與要確認的決定，使提問卡可獨立理解。有依據時可標示建議方案，但不得預設替使用者採用。
- 保留工具提供的自由輸入方式，讓使用者可補充或提出其他方案；若問題尚無可辨識的候選方案，先用自由輸入釐清，不為了可點選而編造方案。
- 核對進度的選項須明確區分「繼續下一條」、「繼續討論本條」與「暫停」。整體檢查後將前進選項寫為「開始第 1 條」；最後一條完成後改為「結束本次核對」，不提供不存在的下一條。
- 使用者實際送出「繼續下一條」或「開始第 1 條」才視為明確要求前進。只確認內容、選擇討論方案或補充規則，不表示同意推進；仍依既有進度規則停在本條。
- 非同步提問工具回傳成功只代表問題已送出，不代表收到答案。等待選擇期間保持進度，不先展開下一條；沉默、逾時、預選值與未送出的選項均不算確認。
- 目前環境沒有可用的互動提問工具，或工具明確回報不支援時，簡短說明限制，才退回文字編號選項；不得把 Markdown 清單、核取方塊或假按鈕宣稱為可點選介面。
- 此規則只調整互動呈現方式，不新增問題、不改變缺失篩選標準，也不因此修改模組文件或取得其他角色權限。

## 每條輸出

先說流程，再說缺失：

1. 用順序步驟解釋觸發條件、身分／資料判斷、驗證、資料寫入與結果；每項附可定位的原文檔案與行號，必要時短引原文。僅解釋該條相關行為。
2. 列出符合下節篩選條件的缺失，每項包含類別、原文位置、具體不確定或衝突，以及它影響哪項決定。多種解讀並列，不代選答案。
3. 沒有符合條件的缺失時明說「本條未發現上述範圍內的缺失」，不可為湊數列一般待辦。
4. 結尾停在本條等待核對，不預先展開下一條；有選項時依「可點選的互動選項」使用原生提問工具。

引用使用已讀取的實際行號與絕對檔案連結。對「未定義」引用最接近且應交代該規則的段落，說明在何種已讀範圍內未找到；不要假裝不存在的規則有原文。

## 缺失篩選

僅列以下事項：

- **邏輯衝突**：文件對相同條件要求互斥行為，或先後步驟無法成立。單純省略文字不直接判為矛盾，須檢查其他段落是否已補足。
- **規則不符**：流程違反來源範圍內明確的規範、資料約束或使用者已確認要求；同時引用規則與不符位置。
- **影響 API 文件的未定義／歧義**：不同合理解讀會改變 API 的必要輸入、身分與授權條件、驗證／拒絕條件、資料寫入與狀態轉換、成功結果或業務錯誤語意。具體指出 API 契約因此無法確定的部分，不泛稱「影響 API」。

排除不影響上述行為的畫面配置、提示文字、導頁、一般實作選擇與最佳實務。HTTP 狀態碼、路由名稱、JSON 欄位命名、錯誤包裝等若可在 API 設計階段決定，不因模組文件未寫就列為缺失；但屬於上述四份文件職責的業務成功／失敗條件若有實質歧義，仍須列出。登入狀態僅在該模組明確負責登入時檢查；否則只說明交接，不要求展開登入設計。

不要要求每份模組文件重複定義已由允許來源中的共用規範負責的事項。未讀或來源範圍外的依賴，與已確認的缺失分開表達。
