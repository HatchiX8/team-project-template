# Tester 輸出規則

Encoding: UTF-8

## 共通原則

- 完成或停止時只在對話中回報，不另建報告檔。
- 分別輸出 `測試狀態：完成／未完成` 與 `結論：PASS／FAIL／未判定`。
- `PASS`：本次必要案例全部執行且符合已核准預期；只代表本次測試範圍通過。
- `FAIL`：至少一項案例已執行，且確認 API 實際結果不符合已核准預期；即使其他案例尚未完成，仍保留已確認的失敗。
- `未判定`：沒有已確認的 API 失敗，但必要案例尚未執行、無法驗證，或預期依據不足；不得將腳本已產生視為通過。
- `測試狀態` 在本次必要案例與結果均已核對時為「完成」；有未執行、無法驗證或必要依據缺口時為「未完成」。
- 測試腳本、環境或資料造成的失敗，先回報原因及影響，不直接當作產品問題或 `FAIL`。
- 每個已確認的產品問題至少引用一項文末實際列出的證據；證據編號使用連續的 `[證據 1]`、`[證據 2]`，同一證據只列一次。
- 不輸出密碼、Token、個資或未遮蔽的敏感請求／回應內容。

## 回覆的區塊順序

1. `## 測試摘要`
2. `## 必須修正`（有已確認的產品問題才顯示）
3. `## 注意事項`（有內容才顯示）
4. `## 改善建議`（有非必要建議才顯示）
5. `## 驗證狀態`
6. `## 檢查範圍`
7. `## 證據`（有實際證據時顯示，永遠最後）

## 測試摘要與判定

- 摘要至少列出模組與 API、測試狀態、結論，以及通過、失敗、無法驗證與未執行的案例數量。
- 若只產生腳本，寫 `測試狀態：未完成`、`結論：未判定`，並標明案例未執行。
- `FAIL` 只用於已確認的 API 行為不符；沒有已確認的 API 失敗但尚有必要案例無法核對時，寫 `未完成／未判定`。
- 即使為 `PASS`，仍要指出本次未涵蓋的 API 或情境；不得擴大成整個模組通過。

```text
## 測試摘要
- 對象：<模組>／<API>
- 測試狀態：完成
- 結論：PASS
- 案例：通過 <數量>、失敗 0、無法驗證 0、未執行 0
- 必須修正：無
```

## 發現項目

- 「必須修正」只列已確認的產品問題；每項包含 API／案例、預期與實際差異、影響、位置或請求資訊，以及證據標記。
- 「注意事項」列測試腳本或環境問題、原因尚未確認的失敗、無法驗證事項、未涵蓋範圍及資料清理限制。
- 「改善建議」只列非必要的後續測試改善，不混入已確認問題。
- 沒有內容時省略對應區塊，不輸出空標題。

```text
## 必須修正
### <API／案例：問題標題>
- 預期：<正式文件要求的狀態碼、參數行為或錯誤格式>。[證據 1]
- 實際：<本次請求觀察到的差異>。[證據 2]
- 影響：<對此 API 使用端的影響>。
- 證據：[證據 1]、[證據 2]
```

## 驗證狀態、檢查範圍與證據

- 「驗證狀態」分列 `已執行`、`未執行／無法驗證` 及原因；記錄實際命令、目標環境與測試資料是否清理完成。
- 「檢查範圍」列出正式文件、模組與 API、產生或修改的腳本、未涵蓋項目、本機 `HEAD` 與相關未提交變更。
- 服務 base URL 與可取得的部署版本列於「檢查範圍」；版本無法確認時明列限制，不宣稱結果對應本機程式碼。
- 「證據」列出必要且可定位的文件位置、腳本位置、命令結果與去識別化的請求／回應事實；使用 `- [證據 N] 來源：已確認事實` 格式，不貼冗長或敏感資料。
- 完成測試的回覆至少提供一項可核對的執行證據；若完全沒有實際證據，省略「證據」並說明尚未取得。

## 中途停止

- 沿用上述區塊順序；摘要寫 `測試狀態：未完成`，指出停止階段、具體原因與下一步。
- 已確認的 API 問題仍以 `FAIL` 及「必須修正」保留；沒有已確認產品問題時寫 `結論：未判定`。
- 「驗證狀態」保留已完成案例與未完成案例的實際狀態；「注意事項」列出環境、腳本或資料清理問題。
- 不把部分完成或未執行的案例稱為通過，也不因中途停止刪除已取得的證據。
