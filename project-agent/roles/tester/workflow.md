# Tester API 測試流程

Encoding: UTF-8

## 1. 確認範圍與依據

- 確認使用者指定的模組與 API。
- 確認本次工作範圍：
  - 產生測試腳本。
  - 執行既有測試腳本。
  - 產生並執行測試腳本。
- 只要求產生腳本時，不自行發送請求。
- 按需讀取以下直接相關文件：
  - `docs/project/` 中的專案規範。
  - `docs/modules/` 中的模組需求。
  - `docs/api-contracts/` 中的 API Contract。
- 只將文件開頭明確標示 `狀態：已核准` 的內容作為正式依據；文件內待確認事項不算正式決策。
- 逐 API 整理必要資訊：
  - HTTP method 與 path。
  - 參數位置與型別。
  - 認證方式。
  - 預期狀態碼。
  - 成功回應與錯誤格式。
- API 或必要預期不明、文件未核准或互相矛盾時，指出缺口並停止；不得從現有回應反推正確答案。
- 記錄測試基準：
  - 本次程式碼的 `HEAD` 與相關未提交變更。
  - 服務 base URL 與執行環境。
  - 可取得的部署版本。
- 遠端服務版本無法確認時，明列限制；不得宣稱測試結果對應本機程式碼。

## 2. 準備腳本與案例

- API 測試腳本統一放在 `apps/server/tests/api/<module>/<feature>.test.ts`。
- 模組專屬測試資料可放在同目錄的 `fixtures/`。
- 只有確實重複使用時才建立 `apps/server/tests/helpers/` 或 `apps/server/tests/fixtures/`。
- 撰寫前查看既有測試與工作區變更，保留他人的工作。
- 沿用可用的測試工具、命令與設定。
- 缺少執行工具或需要調整依賴、package scripts、執行環境時：
  - 回報具體需求。
  - 交由 Developer 處理。
  - 不自行安裝依賴或修改執行環境。
- 每個測試案例都要記錄：
  - 對應 API 與正式文件位置。
  - 請求輸入。
  - 預期結果。
- 依正式文件涵蓋適用案例：
  - 正常請求。
  - 缺少必填參數。
  - 型別、格式或邊界錯誤。
  - 認證或權限錯誤。
  - 其他已定義的錯誤情境。
- 不得憑空指定文件未定義的狀態碼或錯誤訊息。
- 核對參數是否送到正確位置：
  - path。
  - query。
  - header。
  - body。
- 核對回應是否符合預期行為；不能只斷言收到成功回應或任意 2xx 狀態碼。
- 錯誤案例核對 Contract 定義的確切狀態碼及錯誤欄位／代碼。
- 只有文件要求固定錯誤訊息時，才比較完整訊息文字。
- 不為製造 5xx 而破壞服務或資料。
- 測試腳本必須符合以下要求：
  - 包含明確斷言與請求逾時。
  - 斷言失敗時，測試命令必須回傳失敗。
  - 不得捕捉錯誤後仍當作通過。
  - 案例可獨立重跑，不依賴不明的既有資料或執行順序。
- base URL、認證與必要測試資料由既有環境設定或使用者提供。
- 不得硬編碼密碼、Token 或個資，也不得將憑證寫入報告。

## 3. 執行與核對

- 發送請求前確認測試目標：
  - 目標是本機或使用者明確指定的測試環境。
  - 必要認證資料可用。
  - 建立、修改或刪除資料，以及外部通知等副作用都在本次測試範圍內。
- 環境不明或指向正式環境時，停止發送請求並請工程師提供測試目標。
- 涉及資料寫入時：
  - 使用可辨識且可清理的測試資料。
  - 清理範圍只限本次建立的資料。
  - 不刪除既有業務資料。
  - 無法隔離或清理時，回報限制並停止受影響案例。
- 依既有命令執行本次 API 測試，保留實際命令、環境、案例與結果。
- 缺少工具、連線、認證或測試資料時，將受影響案例標記為「無法驗證」。
- 產生測試腳本不代表已執行測試。
- 比對預期與實際狀態碼、參數行為及錯誤格式。
- 發現失敗時先辨識來源：
  - 測試腳本。
  - 測試環境。
  - 產品行為。
  - 原因尚未確認。
- 可修正本次自己造成的測試腳本問題，並重跑受影響案例。
- 產品問題交 Developer 處理；原因不明時明確回報尚未確認。
- 測試結束或中途失敗時，嘗試清理本次建立的測試資料。
- 清理失敗時保留原始測試結果，並回報殘留資料與處理方式。

## 4. 回報

- 依 `output.md` 回報腳本、案例、實際結果與限制。
- 不自動啟動 Developer 或 Review。
- 未執行、跳過、環境阻塞及缺少依據的案例不得列為通過。
- 中途停止時仍保留已完成的結果。
