# Review 輸出規則

Encoding: UTF-8

## 一般原則

- 只在對話中回覆，不建立額外的 Markdown 報告檔。
- 明確說明本次未修改任何專案檔案。
- 沒有風險、無法驗證項或未完成事項時，不建立空泛區塊。
- 不得宣稱未取得的測試／CI 證據已通過，也不得自動啟動 Tester 或其他角色。

## 完成回覆

依檢查規模保持精簡，至少包含：

- 範圍摘要與實際採用的主模式；`paths`／`docs` 應含檢查路徑或文件範圍。
- 測試證據狀態：已納入／未提供／無法驗證（擇一；未涉及測試證據且未要求時可省略）。
- 發現列表：嚴重度、位置、影響、判斷依據。
- 無法驗證的項目（若有）。
- 總結判定：需修改／有條件或需補證／可接受（依 `severity.md`）。

需改碼、補文件或正式測試時，指出應由工程師另行指定 `角色：developer`、`角色：documenter` 或 `角色：tester`，不在本次自動執行。

## 停止回覆

因範圍不明、模式衝突、本階段未支援的檢查方式（相對主幹分支 diff、PR）、缺路徑、必要規則無法讀取、或其他阻礙而停止時，指出停止階段、具體原因、目前已確認的範圍（若有），以及工程師可採取的下一步。範圍不足時，列出目前支援模式與簡短範例，例如：

```text
請明確指定檢查範圍，例如：
- 檢查未提交變更（working-tree）
- 指定路徑（paths）
- 指定文件與實作一致性（docs）
可另加：請一併看測試／CI 結果（測試證據）
（相對主幹分支 diff、PR 檢查尚未納入本階段）
```

不得只說「無法執行」或「載入失敗」。
