# Review module 檢查範圍

Encoding: UTF-8

本文件只建立需求與程式碼的對照範圍，不在此階段判定實作是否正確。

## 定位正式依據

- 依使用者指定的模組名稱定位對象；同名、跨模組稱呼或名稱不足以唯一定位時停止並請使用者確認。
- 按需讀取與該模組相關、已核准的 `docs/project/` 專案規範與架構文件。
- 按需讀取 `docs/modules/` 的模組需求；涉及 API 時，再讀 `docs/api-contracts/` 的對應文件。
- 涉及 Web 或 Server 的架構、狀態管理、資料存取或其他 App 專屬技術約定時，按需查找 `apps/web/docs/` 或 `apps/server/docs/` 的相關文件。必要文件同樣須檢查開頭狀態；草案或未標示核准的內容不能當作正式依據。
- 上述目錄是搜尋層級，不要求全讀，也不假設固定檔名。
- 對每份本次必要的專案、模組與 API 文件，檢查文件開頭的 `狀態` 欄位；只有明確標為 `已核准` 才可作為正式需求。標為 `草稿`、未標示或標示不明時，不得當作已核准；若缺少可替代的已核准正式依據，記錄文件路徑與狀態並停止，不從目錄位置或實作內容推定核准。文件內的待確認事項仍非正式需求。
- README、範本、討論與未核准草案不能取代正式需求；程式碼現狀也不能反推成規格。
- 整理應核對的功能、資料、權限、錯誤情境、對外介面及架構邊界。
- 為每項必要需求記錄正式文件位置與預期行為，交由 `review.md` 逐項核對；不因文件段落未寫成檢查清單而漏掉要求。

## 檢查基準

- 只以目前工作區的程式碼與正式文件為基準；開始 Review 時記錄其狀態，包含模組範圍內已提交、已暫存、未暫存及未追蹤的檔案。本階段不審查歷史版本。
- 記錄當時的 `HEAD` 與相關路徑的 Git 狀態，辨明哪些檔案含未提交內容；只讀取模組及直接關聯路徑，不把其他變更納入 Review。
- 使用者要求以歷史 commit、舊版文件或其他非目前工作區版本為基準時，說明本階段僅支援目前工作區並停止；不得自行改用當前內容給出歷史版本結論。使用者指定的檢查範圍仍須受 `module` 模式的單模組邊界限制。
- 檢查途中相關檔案發生變動時，重新讀取變動檔案並核對受影響的發現、需求條目與證據；無法取得一致基準時回報未完成。

## 定位實作與證據

- 依正式文件與 repository 結構定位實際涉及的 Web、Server 或共用套件程式碼。
- 查找模組入口、匯出、API 呼叫及直接使用端，確認必要的整合邊界；不掃描無關模組或全專案。
- 記錄文件路徑、程式碼路徑、直接關聯範圍、實際技術及可取得的既有測試／CI 證據。
- 文件要求的實作位置缺失時，列為待核對事項；不自行建立檔案。
- 將範圍摘要與無法定位的部分交給 `skill-selection.md` 和 `review.md`。

## 停止與區分

- 必要正式依據缺失、互相矛盾或不足以判斷預期行為時，指出具體文件與缺口後停止正式 Review。
- 已核准技術選型與實際設定不符，且使檢查範圍、準則選取或判準無法確定時，指出兩側依據後停止；不得靜默擇一。
- 正式規格清楚、但程式碼未遵守時，不視為依據矛盾；交由 `review.md` 核對並列為發現。
