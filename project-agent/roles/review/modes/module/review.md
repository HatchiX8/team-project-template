# Review module 檢查規則

Encoding: UTF-8

只檢查 `scope.md` 已確認的模組及直接關聯範圍。

每個發現都須符合 `workflows/common.md` 的證據規則。

## 核心檢查

- **需求覆蓋**：逐項比對模組文件中的功能、輸入輸出、主要流程、錯誤與邊界情境。
- **需求覆蓋**：指出缺漏、行為不符及未實作部分；不能只因程式可編譯就判定需求完成。
- **需求覆蓋**：為 `scope.md` 整理的每項必要需求記錄對應實作或缺失位置，以及「已核對符合／已證實問題／未驗證」其中一種結果；不需另建報告檔。
- **商業邏輯**：從已核准需求明示的流程與限制，推導必然成立的前置條件、狀態轉換、計算結果、資料一致性及權限條件，再核對實作與直接使用端。
- **商業邏輯**：若某個推論存在多種合理解讀，不將偏好的解讀當作隱性規格或已證實 Bug；影響核心判定時依 `scope.md` 停止，否則列為待確認的未驗證事項。

- **模組整合**：核對模組入口、匯出、直接使用端，以及跨 Web／Server 的資料流。
- **模組整合**：檢查是否繞過已核准的層級邊界，或讓相鄰功能依賴錯誤的資料或狀態。

- **API 與資料**：涉及 API 時，比對 Contract 與呼叫端、路由、DTO、錯誤格式及權限要求。
- **API 與資料**：追查資料轉換、執行期輸入驗證、寫入順序與外部副作用的直接影響；TypeScript 型別不能代替執行期驗證。

- **技術準則**：依 `skill-selection.md` 選出的參考文件，獨立核對本次實作相關、可唯讀檢查的技術要求。
- **技術準則**：只把有具體程式位置、影響與依據的偏差列為發現；不執行 Developer 的修改、重構、安裝、建置或測試動作。

- **驗證證據**：只讀使用者提供或可取得的既有測試／CI 結果，確認其與本次模組及目前工作區內容相關。
- **驗證證據**：未提供、無法對應或無法讀取時標示「未驗證」；不自動執行 Tester 或宣稱測試通過。

## 判定邊界

- 發現疑似問題時，先核對正式依據與直接使用端；不把單一函式的局部觀察直接當作模組結論。
- 規格清楚、實作不符時列為發現；規格缺失或矛盾時依 `scope.md` 停止，不自行決定預期行為。
- 未涵蓋的範圍列為「未驗證」；沒有發現不等於全模組沒有風險。
- 不以個人偏好的實作風格取代已核准正式依據。
- 完成前逐項核對需求結果；仍有影響核心流程、權限、資料正確性或 API Contract 的未驗證條目時，依下節視為關鍵缺口。

## 嚴重度分級

- 僅對有具體位置、可確認影響及證據的問題分級；疑點與證據缺口標示「未驗證」，不以推測提高嚴重度。
- 依實際可達的使用者、資料、權限及整合影響分級，不依修改行數、修正難度或個人偏好分級。
- **阻斷**：已證實會造成重大安全或權限破口、資料遺失／不可逆破壞，或使模組核心流程無法使用且無可行替代路徑。
- **嚴重**：已證實違反已核准核心需求、權限、資料正確性或 API Contract，造成主要流程或直接使用端的重要錯誤；未達阻斷程度。
- **中等**：已證實的局部風險或非核心行為問題，不破壞核心需求、權限、資料正確性或 API Contract；有明確影響但未達嚴重程度。
- **輕微**：已證實且影響有限的呈現、可維護性或一致性問題，不改變正式需求與對外行為。
- 若一項問題同時符合多級，採有證據支持的最高級；已證實違反核心需求、權限、資料正確性或 API Contract 時，至少列為「嚴重」。

## 關鍵缺口與結論

- 核心流程、權限、資料正確性或 API Contract 的必要判斷無法核對時，標為「關鍵缺口」；不得把沒有發現問題當成已通過。
- 未取得一般測試／CI 證據時標示「未驗證」，但不單獨形成關鍵缺口；若已核准正式依據明定該證據是驗收必要條件，則列為關鍵缺口。
- 審查狀態與問題結論分開判定：範圍與必要項目核對完畢為「完成」；必要依據、關鍵項目或一致的程式碼基準無法確認時為「未完成」。
- 已證實至少一項阻斷或嚴重問題時，問題結論為 `FAIL`；即使其他部分使審查狀態為「未完成」，仍保留已證實問題並揭露未驗證範圍。
- 沒有已證實的阻斷或嚴重問題、但審查狀態為「未完成」時，問題結論為「未判定」，不得以缺口推定 `FAIL`。
- 審查狀態為「完成」、沒有已證實的阻斷或嚴重問題時，問題結論為 `PASS`，僅限本次已檢查範圍；中等與輕微問題仍須回報。
