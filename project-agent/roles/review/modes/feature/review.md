# Review feature 檢查規則

Encoding: UTF-8

只檢查 `scope.md` 已確認的單一功能及直接關聯範圍。每個發現都須符合 `workflows/common.md` 的證據規則；不得將本模式的結果宣稱為整個模組的結論。

## 核心檢查

- **需求覆蓋**：逐項核對該功能已核准的輸入輸出、正常流程、錯誤與邊界情境，以及直接相關的資料、權限和 API 要求；不能只因程式可編譯就判定需求完成。
- **需求覆蓋**：為 `scope.md` 整理的每項必要需求記錄對應實作或缺失位置，以及「已核對符合／已證實問題／未驗證」其中一種結果；不需另建報告檔。
- **商業邏輯**：從已核准需求明示的限制推導必然成立的前置條件、狀態轉換、計算結果、資料一致性與權限條件，再核對功能入口至直接使用端的實作。
- **商業邏輯**：存在多種合理解讀時，不把偏好當作隱性規格或已證實 Bug；影響本功能核心判定時依 `scope.md` 停止，否則列為待確認的未驗證事項。
- **功能整合**：檢查該功能的入口、呼叫鏈、回傳結果及直接使用端；橫跨 Web／Server 時核對直接資料流。共用程式碼造成的可證實回歸風險，只回報與指定功能直接相關的影響。
- **API 與資料**：涉及 API 時，比對相關 Contract 與呼叫端、路由、DTO、錯誤格式及權限要求；追查本功能的資料轉換、執行期輸入驗證、寫入順序與外部副作用。TypeScript 型別不能代替執行期驗證。
- **技術準則**：依 `skill-selection.md` 選出的參考文件，獨立核對本功能相關且可唯讀檢查的技術要求；只把有具體程式位置、影響與依據的偏差列為發現，不執行 Developer 或 Tester 工作。
- **驗證證據**：只讀使用者提供或可取得的既有測試／CI 結果，確認其與本功能及目前工作區內容相關；未提供或無法對應時標示「未驗證」，不宣稱測試通過。

## 判定邊界

- 發現疑似問題時，先核對正式依據、功能呼叫鏈與直接使用端；不把單一函式的局部觀察直接當作功能結論。
- 規格清楚、實作不符時列為發現；規格缺失或矛盾時依 `scope.md` 停止，不自行決定預期行為。
- 未涵蓋的範圍列為「未驗證」；本功能未發現問題不等於整個模組沒有風險。
- 不以個人偏好的實作風格取代已核准正式依據，也不因檢查直接使用端就對另一項功能作完整判定。
- 完成前逐項核對本功能必要需求；仍有影響本功能核心流程、權限、資料正確性或 API Contract 的未驗證條目時，視為關鍵缺口。

## 嚴重度分級

- 僅對有具體位置、可確認影響及證據的問題分級；疑點與證據缺口標示「未驗證」，不以推測提高嚴重度。
- 依對指定功能及其直接使用端實際可達的使用者、資料、權限及整合影響分級，不依修改行數、修正難度或個人偏好分級。
- **阻斷**：已證實造成重大安全或權限破口、資料遺失／不可逆破壞，或使指定功能的核心流程無法使用且無可行替代路徑。
- **嚴重**：已證實違反該功能已核准的核心需求、權限、資料正確性或 API Contract，造成主要流程或直接使用端的重要錯誤；未達阻斷程度。
- **中等**：已證實的局部風險或非核心行為問題，不破壞該功能的核心需求、權限、資料正確性或 API Contract；有明確影響但未達嚴重程度。
- **輕微**：已證實且影響有限的呈現、可維護性或一致性問題，不改變正式需求與對外行為。
- 同時符合多級時，採有證據支持的最高級；已證實違反本功能核心需求、權限、資料正確性或 API Contract 時，至少列為「嚴重」。

## 關鍵缺口與結論

- 本功能核心流程、權限、資料正確性或 API Contract 的必要判斷無法核對時，標為「關鍵缺口」，不得把沒有發現問題當成已通過。
- 未取得一般測試／CI 證據時標示「未驗證」，但不單獨形成關鍵缺口；若已核准正式依據明定該證據是驗收必要條件，則列為關鍵缺口。
- 審查狀態與問題結論分開判定：指定功能的範圍與必要項目核對完畢為「完成」；必要依據、關鍵項目或一致的程式碼基準無法確認時為「未完成」。
- 已證實至少一項阻斷或嚴重問題時，問題結論為 `FAIL`；即使審查狀態為「未完成」，仍保留已證實問題並揭露未驗證範圍。
- 沒有已證實的阻斷或嚴重問題、但審查狀態為「未完成」時，問題結論為「未判定」，不得以缺口推定 `FAIL`。
- 審查狀態為「完成」、沒有已證實的阻斷或嚴重問題時，問題結論為 `PASS`，僅限指定功能的已檢查範圍；中等與輕微問題仍須回報。
