# Documenter 文件撰寫與整理準則

Encoding: UTF-8

本文件適用於 Documenter 的工程規範、架構說明、操作文件及其他指定文件工作。它規範內容如何呈現與核對，不替團隊決定需求，也不新增各類文件的必要章節範本。

## 1. 讀者與文件用途

- 以工程師與新進人員的閱讀需求為優先，讓 Agent 也能理解內容。
- 先回答「這份文件有什麼用」與「我要怎麼做」，再說明限制與背景。
- 基本內容不要求讀者先理解內部分類、角色流程或讀完其他文件。
- 本次文件工作以能支援指定用途、操作與判斷為目標，不以篇幅或規則數量衡量。
- 未有各類文件必要內容標準時，不以此目標宣稱文件完整或符合所有開發與測試需求。

## 2. 長期原則、專案約定與待確認事項

| 分類 | 判斷方式 | 說明性例子 |
| --- | --- | --- |
| 長期原則 | 不因新增功能、模組或日常設定調整而改變 | 必須一起成功的寫入使用同一交易；不記錄敏感資料 |
| 專案設定與約定 | 由目前專案選型、設計或環境決定 | 套件版本、目錄、命名格式、保留天數、共用欄位、重試政策 |
| 待確認事項 | 尚未經工程師確認的內容 | 重試次數、佇列參數、未定案格式 |

- 表中例子用於說明分類，不因此成為本專案的正式規則。
- 不因原文使用「必須」或「禁止」，就將內容歸為長期原則。
- 長期原則不隨日常專案變更調整，不代表永遠不能修改。
- 日常維護集中於專案設定與約定；本次修改影響操作步驟或引用時，在授權範圍內同步更新。
- 分類依已確認的內容與適用範圍，不將團隊共用約定擅自改為專案專屬規則。
- 無法判定分類且會改變內容意義時，列為待確認，不自行補成政策。

## 3. 閱讀順序與呈現方式

規範型文件建議依序呈現：

1. 用途與常用做法。
2. 長期原則。
3. 專案設定與約定。
4. 待確認事項。
5. 相關文件。

- 開頭以一至兩句話交代用途，避免先堆疊範圍聲明或大量連結。
- 適用範圍仍須清楚，可依文件用途自然安排，不因簡化開頭而省略必要條件。
- 比較資訊用表格，操作流程用有序步驟，必要時提供簡短例子。
- 規則條列以一項主要要求為單位，條件、例外與後果維持清楚關聯。
- 文件可依用途調整閱讀順序與結構，不強迫架構或操作文件套用全部章節。
- 不為符合格式而補寫沒有依據的內容，也不保留不適用的空白章節。
- 沿用 `docs/templates/documentation-standard.md` 的適用呈現規範，不另建立重複的 Markdown 公版。

## 4. 自然用語與技術精確性

- 優先使用工程師熟悉的詞彙。
- 必要術語第一次出現時，提供簡短解釋，後續保持一致。
- 缺少背景的內部分類，例如「深度 D1」或「寫法 A」，改為讀者能理解的描述；有必要保留時補充其意義。
- 規則直接說明條件、做法與必要理由，減少「嚴格禁止」或「無例外」等反覆強調。
- 簡化文字時保留原要求強度，不能將「必須」改成建議或省略原有例外。

| 較難理解的表達 | 可採用的說明方式 |
| --- | --- |
| 同成同敗 | 全部成功或全部回滾 |
| 失敗可觀察性 | 失敗時留下可追查的紀錄 |
| 必須可冪等 | 重複執行時不產生額外影響，並補充適用條件與必要技術說明 |

- 表中用語只是表達示例，不是固定替換表；替換仍須符合原技術語意與適用條件。

## 5. 命名與既有慣例

- 沿用已確認的程式、資料表、欄位與檔案名稱。
- 不為改善文件文字而自行改名或另創同義名稱。
- 清楚區分型別名稱、型別內欄位與資料庫欄位等不同命名對象。
- 命名規則有歧義時，指出具體問題並列為待確認，不自行推定團隊慣例。

## 6. 單一維護來源與引用

- 每項主題確認主要文件，其他文件以連結引用；來源不明時先提出待確認事項。
- 導讀可保留摘要，但須指出詳細規則來源，不另維護一份完整規則。
- 共用原則、模組業務規則、個別資料表與維運操作，分別放在已確認負責的文件。
- 避免在核心規則、操作說明與禁止事項反覆重述相同要求。
- 避免複製其他文件的狀態描述；必要時引用來源並核對資訊一致。
- 需要搬移內容或更新授權範圍外的關聯文件時，先說明影響並取得工程師指示，不順手擴大修改。

### 參照式連結

- 新增或整理文件引用時，使用 Markdown 參照式連結，讓正文可以直接點擊，連結目標集中於文件末尾維護。
- 顯示文字與識別名稱相同時使用 `[名稱]`；不同時使用 `[顯示文字][識別名稱]`，例如資料表名稱含程式碼格式時使用後者。
- 在文末以 `[識別名稱]: 相對路徑` 定義目標，每個目標原則上只定義一次。需要連到不同章節時，可分別定義包含章節錨點的目標。
- 「關聯文件」保留可點擊的參照式連結，並簡短說明用途；連結定義放在清單之後，不寫成清單項目，也不把目標包成 `(相對路徑)`。
- 正文在需要查看規則依據、詳細流程或相關資料時提供連結；同一段或條列內重複提到相同來源時，通常連結一次即可。
- 不因網址集中維護而移除正文的跳轉能力，也不要求每次提到名稱都加上連結。
- 重複引用同一來源不等於重複維護規則；避免的是另寫一份完整規則，不是必要的閱讀連結。

以下以模組概覽為例；實際相對路徑以所在文件為準：

```markdown
憑證輪替與撤銷見 [bindingCredentials]，使用者欄位見 [`users` schema][users-schema]。

## 關聯文件

- [bindingCredentials]：憑證核發、輪替與撤銷。
- [`users` schema][users-schema]：系統使用者資料表。

[bindingCredentials]: ../bindingCredentials/overview.md
[users-schema]: ../../schemas/users.md
```

## 7. 整理與決策的邊界

- 清楚標示文件狀態；整理成新文件不自動取得來源文件的核准狀態。
- 狀態的欄位名稱、粗體與句號依公版文件規範及 `workflow.md` 的格式要求，不自行省略或替換。
- 文件狀態的更新統一依 `workflow.md` 的文件調整規則處理，不自行核准。
- 已定要求、建議方案與待確認事項須明確區分。
- 範例須區分正式約定與示意，避免候選格式被誤認為標準。
- 原文只有 TODO 時，只整理已知缺口，不自行補成正式政策。
- 文件內的待確認事項依以下固定格式整理，完整示例見 `docs/templates/documentation-standard.md`：
  - 以 `## 待確認事項` 集中呈現，各問題使用 `### <問題名稱>`。
  - 必要欄位依序為 `**背景**`、`**待決定問題**` 與 `**決策結果**`，各欄位獨立一行，內容另起段落。
  - 有已知方案時，在待決定問題與決策結果之間加入 `**候選方案**`，以有序清單列出；沒有方案時省略，不自行補造。
  - 尚未決定時，決策結果寫 `待確認。`；有已知的後續文件更新需求，可補充 `待確認；須另行更新 <文件路徑>。`。
  - 後續更新需求只作記錄，不代表授權修改範圍外文件。
- 發現衝突時保留具體差異與需工程師確認的問題，不透過改寫文字掩蓋差異。
- 工程師確認決策後，移入對應章節並移除已解決的待確認項目；相關文件狀態仍依既有核准規則處理。

## 8. 完成前的內容與閱讀路徑核對

- 核對來源與整理結果，確認要求、適用條件、強度與例外未因簡化而遺失或改變；已確認的政策修訂則對照工程師決策，避免反向套用或擅自採用建議。
- 檢查 UTF-8、相對連結、章節引用、表格與程式碼區塊。
- 核對正文與關聯文件的參照名稱都有對應定義，目標路徑及章節錨點有效；同一識別名稱不得指向不同目標，避免未定義的 `[名稱]` 被呈現為普通文字。
- 有待確認事項時，核對問題標題、必要欄位、候選方案的適用性及決策結果，不混入已定要求。
- 在指定文件與必要關聯範圍內，確認沒有重複維護或互相矛盾的約定，不因此掃描全專案。
- 多份文件需一起閱讀時，提供簡短入口，依工作情境引導閱讀。
- 回報實際核對範圍與限制；只整理文字時，不宣稱已驗證程式、套件或執行行為。

## 9. 問題判定原則

- 建議的章節順序或表達示例，不是強制合格條件。
- 已確認問題須指出文件位置、原描述、直接依據與對指定用途的影響；不以偏好或通用慣例代替必要內容標準。
- 單純用詞偏好、不同但合理的結構或尚無依據的完整性期待，列為補充建議，不當作正式缺失。
- 沒有已核准的必要內容標準時，不因缺少特定章節判定文件不合格。
