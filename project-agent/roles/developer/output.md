# Developer 輸出規則

Encoding: UTF-8

## 執行結果

- 唯讀分析只在對話中回覆已確認的行為、來源路徑、結構推論與待確認事項，不建立額外的 Markdown 報告，並明確說明本次未修改檔案。
- 開發任務應保留足以回報的事實：修改檔案、完成需求、已執行驗證及結果、未能執行的驗證及原因、未完成事項，以及需人工確認的風險。

## 完成回覆

- 依任務規模保持精簡，至少說明完成內容、主要修改檔案或範圍、驗證方式與結果。
- 驗證失敗、關鍵驗證無法執行、部分需求未完成，或發現重大 API Contract、資料、權限風險時，須明確說明；沒有風險或未完成事項時，不建立空泛區塊。

- 執行既有測試與手動驗證，不代表已完成 Tester 的正式測試。
- 不得宣稱未執行的驗證已通過，也不得自動啟動 Tester。

## 跨模組修改的階段回報

- 規劃時分別列出要修改的業務模組、共用內容、階段數與順序，以及各階段修改範圍、完成條件與驗證方式，不另建報告檔。
- 有共用內容時，列明檔案路徑、歸屬階段與受影響使用端，不只回報模組數量。
- 每階段結束後說明目前第幾階段、修改單位（模組或共用內容）、本階段修改檔案與範圍、完成內容及驗證結果。
- 分列未完成事項、相依阻礙與需要工程師確認的內容；沒有項目時保持精簡。
- 有後續階段時，明確表示「等待工程師確認」，並說明確認後預計進入的階段；輸出後停止本輪修改。
- 已知相依失敗需工程師明確允許帶著阻礙繼續，不得只因收到一般確認就略過。
- 階段完成不得寫成整體任務完成，也不因暫停確認就假稱發生文件缺口。
- 最終回覆摘要各階段結果與整合驗證，保留未解除的失敗或未驗證事項。

## 停止回覆

- 因正式依據缺失、矛盾、語意不足或其他阻礙而停止時，指出停止階段、具體原因、涉及的文件或路徑、已完成與尚未完成的修改，以及工程師可採取的下一步。
- 若需修正正式文件，說明應由 Documenter 或工程師調整，並待工程師明確指示後才可恢復；不得只說「無法執行」。
