# Developer 一般開發流程

Encoding: UTF-8

本流程適用於新增或改變系統行為，以及影響 API、資料結構、權限、依賴或跨模組介面的工作。

- 文件核准依 `entry.md` 的共同規則確認；本次任務指令不取代必要依據的核准檢查。

1. 先依任務描述與現有實作辨識受影響範圍；修改共用或被外部引用的內容前，查找相關引用與使用端，不只看預計修改的函式。
   - 再按下列三層查找**本次必要且已核准**的正式依據。
   - 資料夾是搜尋範圍，不代表其中每份文件都要讀；依內容與責任找到對應文件及章節，不假定未來的檔名或模組名稱。
   - **專案層 `docs/project/`**：讀取與本次工作有關的共同準則，例如命名、架構邊界或環境規則；專案層級變更須確認其對應依據。
   - **模組層 `docs/modules/`**：涉及模組行為或資料時，依任務與程式碼定位所屬模組，讀取每個受影響模組的相關文件；跨模組工作須涵蓋所有受影響模組。
   - **API 層 `docs/api-contracts/`**：涉及 API 介面、資料傳輸、驗證、錯誤或行為約定時，讀取每個受影響 API 的 Contract；未影響 API 時不為了湊齊三層而讀取。
   - **App 專屬文件 `apps/web/docs/`、`apps/server/docs/`**：涉及對應 App 的架構、狀態管理、資料存取或其他技術約定時，按需查找相關文件。
     - 這是三層正式依據之外的補充搜尋範圍；必要文件仍須依 `entry.md` 檢查開頭狀態，草案或未標示核准的內容不能當作正式依據。
2. `README.md` 可用來定位文件，但目錄說明不能取代對應規格。
   - 若無法確定應對哪個模組、API 或正式文件，不自行猜測；指出已查找的範圍與缺口，依 `entry.md` 停止。
3. 修改前比對必要文件與任務要求，確認預期行為及影響邊界清楚；再比對現有實作，辨識要修正的差異。
   - 文件與任務的預期一致、但程式不符合文件時，可以依據文件修正，不把 Bug 當成文件衝突。
   - 必要文件缺失、僅有 TODO／未核准草案、正式依據彼此矛盾，或缺少會影響需求、對外行為、資料、權限或架構邊界的決策時，依 `entry.md` 停止；不以程式碼現況、Notion 討論或評估報告自行補成規格。
   - 內部實作細節依既定規範由 Developer 判斷。

前置檢查通過後，執行已載入的 `project-agent/roles/developer/workflows/development.md`，不另建一套實作、驗證或回報流程。
