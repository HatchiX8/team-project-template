# Developer 修改後驗證與自我檢查

Encoding: UTF-8

本文件只供已產生修改的 Developer 任務使用；唯讀分析不載入。

依本次變更選擇相關檢查，不要求每次執行全部工具；自我檢查只檢視本次修改與直接影響範圍，不藉此擴大重構。

## 驗證前判斷與選擇

- 執行驗證前，先檢查本次實際 diff，依修改內容與影響範圍選擇最低必要驗證。
- 不只依副檔名、修改行數或使用者稱為「小修改」判定驗證需求。
- 同時包含多種修改時，合併各類適用的驗證，不以較低風險類別取代其他必要檢查。
- 修改共用內容、匯出介面或檔案路徑時，先查找引用與使用端，再決定受影響的 App、套件與模組。
- 向使用者簡短說明本次修改類別、選擇的驗證與範圍，以及可免執行項目的理由；不另建驗證計畫文件。

### 最低驗證對照

| 修改內容 | 最低驗證 |
| --- | --- |
| 純文件文字、一般說明註解 | 檢查實際 diff；可免 typecheck／build |
| 變數、函式、型別、檔案命名 | lint、typecheck；再依引用與行為影響補充既有測試及手動驗證 |
| 邏輯、API、資料模型、相依套件、建置設定 | 相關既有測試與可行的手動驗證，以及對應的 typecheck／build；涉及程式碼品質檢查時執行相關 lint |

### 純文字與註解的適用邊界

- 純文字類別只適用於不改變正式需求、API Contract、程式行為、型別、工具行為或建置結果的修改。
- 一般說明註解須確認未意外修改程式碼、字串內容或註解邊界。
- `@ts-ignore`、`@ts-expect-error`、三斜線指令、ESLint 指令、影響型別的 JSDoc 或供工具解析的註解，不屬於一般說明註解。
- 特殊註解依其實際影響選擇 lint、typecheck、build 或相關既有測試。
- 純文字修改至少核對內容正確性、相關連結或引用，以及本次完成條件。
- 純文字修改不強制執行與其無關的 lint、既有測試或執行期手動操作。

### 命名與功能變更的選擇

- 程式命名變更執行相關 lint 與 typecheck，並確認引用、匯出與使用端同步。
- 檔案更名涉及路徑解析、大小寫、路由、動態載入或打包結果時，補充相關 build 與可行的行為驗證。
- 邏輯、API 或資料模型變更，執行直接相關的既有測試與可行的行為驗證。
- 影響 TypeScript 程式、型別、型別解析或編譯設定時，執行對應 typecheck。
- 影響建置流程、打包、輸出或執行期載入時，執行對應 build。
- 相依套件或設定變更同時影響型別與建置時，兩項都須執行。
- 無法確定某項檢查是否可免執行時，不直接套用純文字豁免；依可確認的影響補充驗證，或回報無法確認的原因。

## 執行驗證

- 依前段選擇結果，使用專案既有的驗證工具、命令與設定。
- lint 可使用既有工具支援的檔案範圍，但須涵蓋本次修改的相關程式碼或設定。
- typecheck 以受影響的既有 TypeScript 專案或 workspace 為範圍；共用型別或介面變更時，納入受影響的使用端。
- 專案已配置增量檢查或相依圖工具時，可沿用其快取與範圍選擇機制。
- 不以單獨指定變更檔案、臨時縮小 tsconfig 的 include，或省略使用端來冒充完整的相關型別檢查。
- 目前沒有模組級檢查機制時，執行所屬 App 或套件的既有 typecheck，不自行建立臨時檢查邊界。
- 選定的必要檢查缺少工具、命令或相關既有測試時，依下方規則回報未驗證項目與原因。
- 不建立或修改測試腳本、測試案例；正式測試由 Tester 負責。
- 完成回覆區分已執行、依修改性質免執行與必要但無法執行的項目，不將免執行或未執行寫成通過。

## 失敗與未執行項目

- 不得忽略與本次修改相關的 build、lint 或 typecheck 失敗。
- 相關檢查仍失敗時，不得宣稱驗證通過或無條件完成。
- 驗證失敗時，比對修改範圍與可用的修改前結果。
- 修正本次修改造成的問題，並重新驗證受影響部分。
- 有證據確認失敗原本存在且與本次修改無關時，不擴大範圍修正，但須如實回報。
- 無法確認失敗來源時，記錄「原因尚未確認」；不得逕稱既有問題或宣稱驗證通過。
- 無法執行檢查時，記錄未驗證項目、原因與工程師可執行的指令；完成回覆依 `output.md`。

## 自我檢查

### 範圍與需求

- 是否逐項完成修改前確認的可觀察條件；未完成時不得宣稱需求全部完成。
- 是否只修改本次任務及直接關聯的必要檔案。
- 是否出現未授權的功能刪除或 public API 變更。
- 既有檔案更名、目錄移動或關聯模組修改是否符合 `restrictions.md`，並已說明原因。

### 資料流與架構

- 資料來源、更新順序、狀態管理與對外 Contract 的變更，是否符合本次任務及已核准正式依據；未授權部分是否維持既有行為。
- 是否繞過既有流程或引入隱式共享狀態。
- 是否保持責任邊界，且未引入違反專案分層規則的依賴或繞過規定的層級邊界。
- 是否產生重複商業邏輯、過度耦合或不必要的抽象化。

### 程式品質與驗證結果

- 是否因本次修改留下未使用的 import 或變數。
- 是否產生重複程式碼、過深分支或難以理解的命名。
- 是否記錄實際執行的 lint、typecheck、build、既有測試與手動驗證結果。
- 失敗及未執行項目是否依本文件處理並記錄；不得藉清單修正無關問題。
